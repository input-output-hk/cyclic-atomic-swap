## 11.2 Risks

### 11.2.1 MuSig2 Curve Compatibility

A MuSig2 signature is just a standard Schnorr signature (R, s) from the verifier's perspective — the multi-party
ceremony is invisible. So:

- A MuSig2 signature on [secp256k1](https://en.bitcoin.it/wiki/Secp256k1)
  is verifiable by any standard secp256k1 Schnorr verifier (e.g. Bitcoin nodes via
  [BIP-340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)).
- A MuSig2 signature on [ristretto255](https://ristretto.group/) is verifiable by any ristretto255 Schnorr verifier
- They are not cross-curve compatible — the curve is baked into the signature's group arithmetic.

The [MuSig2 paper (Nick, Ruffing, Seurin, 2021)](https://eprint.iacr.org/2020/1261) specifies requirements in terms of
an abstract group, not a concrete curve. MuSig2 needs

- a prime-order group (or prime-order subgroup) where the Discrete Logarithm Problem is hard,
- a Schnorr-compatible signature equation over that group,
- a collision-resistant hash function (modelled as a random oracle).

**Where MuSig2 Is Currently Standardised**

| Instantiation     | Status                                                            |
|-------------------|-------------------------------------------------------------------|
| secp256k1         | BIP-327 (Bitcoin standard) — most mature.                         |
| secp256r1 (P-256) | Used in some FIDO2 / passkey contexts.                            |                            
| ristretto255      | Increasingly common in privacy protocols (e.g. Signal ecosystem). |
| Ed25519           | Used with care — cofactor 8 requires extra handling.              |
| P-384, P-521      | Possible, no wide deployment.                                     |

[P-384](https://en.wikipedia.org/wiki/P-384) and
[P-521](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/P521_SHA512.pdf)
are the elliptic curve for the
[ECDSA](https://en.wikipedia.org/wiki/Elliptic_Curve_Digital_Signature_Algorithm)
and [ECDH](https://en.wikipedia.org/wiki/Elliptic-curve_Diffie%E2%80%93Hellman) algorithms.

ECDSA produces a signature pair (r, s) where r is derived from a random nonce point on the curve,
and s involves modular inverse operations.
The verification equation is non-linear and requires two separate scalar multiplications.

Schnorr produces a pair (R, s) where the signature equation is linear: s = r + H(R || P || m) * x (nonce + hash *
private key).
Verification checks s·G = R + H(R||P||m)·P.

Bitcoin used ECDSA (secp256k1 curve) originally and added Schnorr
via Taproot ([BIP-340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)) in 2021.

Edwards curves like [Ed25519](https://ed25519.cr.yp.to/) are popular for Schnorr-style signatures (EdDSA),
but they have cofactor of 8, which creates subtle issues for MuSig2:

- Small-subgroup attacks become possible if points aren't validated
- The prime-order assumption in MuSig2's proof doesn't hold directly
- Cofactor needed for clearing or to work in the ristretto255 abstraction,
  which essentially presents a prime-order group built on top of Ed25519.

The ristretto255 is the preferred choice when you want MuSig2 on a modern fast curve — it provides the
performance of Edwards arithmetic with a clean prime-order group.

[BLS12-381](https://eips.ethereum.org/EIPS/eip-2333)'s G1 subgroup is a prime-order group where
the Discrete Logarithm Problem is hard, so MuSig2's requirements are satisfied.
The practical obstacles are that G1 arithmetic is significantly heavier than secp256k1 or ristretto255,
no standard or peer-reviewed security proof exists for this instantiation,
and the curve's non-trivial cofactor requires explicit subgroup clearing on all points.
Crucially, MuSig2 uses only the group law and never touches the bilinear map that justifies BLS12-381's existence
as a curve choice.
If the goal is multi-party or aggregated signing on BLS12-381,
native BLS signature aggregation is the purpose-built alternative:
it is non-interactive, natively supported by the curve, and standardised in IETF RFC 9380.

### 11.2.2 MuSig2 Bridge Pattern for Incompatible Curves.

The [swap-validator](https://github.com/swap-exchange/swap-validator) provides the smart-contract Cardano uses
to bridge between MuSig2 for secp256k1 and Cardano cryptography based on ed25519.
The idea is to implement in the smart-contract a MuSig2 validator.
The party redeeming a spend<sup>tx</sup> calls the smart-contract with the MuSig2 signed transaction id of the Cardano
lock<sup>tx</sup> the party is redeeming.
If the signature is valid, the smart-contract uses the ed25519 signed transaction to commit the spend<sup>tx</sup>.

> When blockchains use different curves, the same pattern can be used: implement a MuSig2 validator in the
> smart-contract.
